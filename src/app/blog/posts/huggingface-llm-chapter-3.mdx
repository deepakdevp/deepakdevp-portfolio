# Fine-Tuning: Making Models Your Own

Chapters 1 and 2 of the HuggingFace course taught me how transformers work and how tokenization shapes their understanding. But I was still using pre-trained models out of the box.

Chapter 3 changed that. This is where you learn to **fine-tune** models — taking a pre-trained model and adapting it to your specific task.

And it's shockingly effective.

## The Fine-Tuning Workflow

The core idea: instead of training a model from scratch (which requires millions of examples and weeks of GPU time), you:

1. Start with a pre-trained model (e.g., `bert-base-uncased`)
2. Add a task-specific head (e.g., a classification layer)
3. Train on a small dataset (hundreds to thousands of examples)
4. Get domain-specific performance in hours, not weeks

The pre-trained model already knows:
- Grammar
- Syntax
- General semantics
- Common sense

You're just teaching it the nuances of *your* problem.

## My Real-World Use Case: Ticket Classification

At work, we have an internal support system. Engineers file tickets for infrastructure issues, feature requests, bugs, and questions.

Currently, someone manually categorizes each ticket:
- `infrastructure` → Goes to DevOps
- `bug` → Goes to engineering team
- `feature-request` → Goes to product
- `question` → Goes to support

This takes time and is error-prone. Sometimes tickets get miscategorized and bounce between teams.

**My goal**: Fine-tune a BERT model to auto-classify tickets.

## Step 1: Prepare the Dataset

I exported 2,000 historical tickets from our system. Each ticket has:
- Title
- Description
- Category (label)

I combined title + description into a single text field:

```python
import pandas as pd

data = pd.read_csv('tickets.csv')

data['text'] = data['title'] + ' ' + data['description']
data = data[['text', 'category']]

# Check distribution
print(data['category'].value_counts())

# Output:
# bug                 650
# infrastructure      520
# feature-request     480
# question            350
```

Not perfectly balanced, but good enough. If it were severely imbalanced (e.g., 90% bugs), I'd need to oversample or use class weights.

## Step 2: Tokenize the Data

Using BERT's tokenizer:

```python
from transformers import AutoTokenizer

tokenizer = AutoTokenizer.from_pretrained('bert-base-uncased')

def tokenize_function(examples):
    return tokenizer(examples['text'], padding='max_length', truncation=True, max_length=512)

from datasets import Dataset

dataset = Dataset.from_pandas(data)
tokenized_dataset = dataset.map(tokenize_function, batched=True)
```

Key points:
- `padding='max_length'` ensures all inputs are the same length (required for batching)
- `truncation=True` cuts off text longer than 512 tokens
- `batched=True` processes multiple examples at once (faster)

## Step 3: Define the Model

I used `AutoModelForSequenceClassification`, which loads BERT and adds a classification head on top.

```python
from transformers import AutoModelForSequenceClassification

model = AutoModelForSequenceClassification.from_pretrained(
    'bert-base-uncased',
    num_labels=4  # 4 categories
)
```

Under the hood:
- BERT's 12 transformer layers stay the same (pre-trained weights)
- A new linear layer is added on top: `768 hidden units → 4 output classes`

During fine-tuning, all layers get updated, but the pre-trained layers change slowly (low learning rate), while the classification head learns from scratch (higher learning rate).

## Step 4: Training with the Trainer API

HuggingFace's `Trainer` API abstracts away most boilerplate:

```python
from transformers import Trainer, TrainingArguments

training_args = TrainingArguments(
    output_dir='./results',
    eval_strategy='epoch',
    learning_rate=2e-5,
    per_device_train_batch_size=16,
    per_device_eval_batch_size=16,
    num_train_epochs=3,
    weight_decay=0.01,
)

trainer = Trainer(
    model=model,
    args=training_args,
    train_dataset=tokenized_dataset['train'],
    eval_dataset=tokenized_dataset['test'],
)

trainer.train()
```

**Training parameters explained:**

- `learning_rate=2e-5`: Small learning rate to avoid catastrophic forgetting (overwriting pre-trained knowledge)
- `num_train_epochs=3`: Usually 2-5 epochs is enough for fine-tuning
- `weight_decay=0.01`: Regularization to prevent overfitting
- `batch_size=16`: Fit within GPU memory (I used a T4 on Google Colab)

Training took about 20 minutes on a T4 GPU.

## Step 5: Evaluation

After training, I evaluated on a held-out test set (300 tickets):

```python
from sklearn.metrics import classification_report

predictions = trainer.predict(tokenized_dataset['test'])
predicted_labels = predictions.predictions.argmax(-1)
true_labels = tokenized_dataset['test']['label']

print(classification_report(true_labels, predicted_labels, target_names=['bug', 'feature-request', 'infrastructure', 'question']))
```

Results:

**89% accuracy** — way better than I expected!

For comparison, I tested a zero-shot classifier (no fine-tuning):

```python
from transformers import pipeline

classifier = pipeline('zero-shot-classification')
result = classifier("Our CI/CD pipeline is broken", candidate_labels=['bug', 'feature-request', 'infrastructure', 'question'])
```

Zero-shot accuracy: ~65%

Fine-tuning gave a **24% improvement**.

**Predicted**: `infrastructure`  
**Actual**: `infrastructure`  
✅ Correct

**Input**: "Can we add dark mode to the dashboard?"  
**Predicted**: `feature-request`  
**Actual**: `feature-request`  
✅ Correct

**Input**: "How do I reset my password?"  
**Predicted**: `question`  
**Actual**: `question`  
✅ Correct

## Where It Failed

Some interesting failures:

**Input**: "The login button doesn't work on mobile"  
**Predicted**: `feature-request`  
**Actual**: `bug`  
❌ Wrong

The model saw "mobile" and "login button" and thought it was a feature request (maybe "add mobile support"). It missed the "doesn't work" part.

**Fix**: I added more training examples with negative phrasing ("doesn't work", "broken", "fails").

**Input**: "Why is the API rate limit so low?"  
**Predicted**: `question`  
**Actual**: `feature-request`  
❌ Wrong (but understandable)

This one's subjective. "Why is X?" sounds like a question, but the intent is probably "can we increase the rate limit?" (a feature request).

**Fix**: This might require multi-label classification (it's both a question *and* a feature request).

## Step 6: Deploying the Model

I saved the fine-tuned model and deployed it as a FastAPI endpoint:

```python
from transformers import pipeline

classifier = pipeline('text-classification', model='./fine-tuned-bert')

from fastapi import FastAPI

app = FastAPI()

@app.post('/classify')
def classify_ticket(text: str):
    result = classifier(text)
    return {'category': result[0]['label'], 'confidence': result[0]['score']}
```

Now our ticketing system auto-suggests a category when engineers create a ticket. They can override it if it's wrong, but 89% of the time it's correct.

**Impact:**
- **Time saved**: ~5 hours/week (no manual categorization)
- **Routing accuracy**: Increased from ~85% (human) to 89% (model)
- **Faster response times**: Tickets go to the right team immediately

## Fine-Tuning vs. Prompt Engineering

You might ask: "Why not just use GPT-4 with a good prompt?"

I tried that too:

```python
prompt = f"""
Classify this support ticket into one of: bug, feature-request, infrastructure, question.

Ticket: {ticket_text}

Category:
"""

response = openai.Completion.create(model='gpt-4', prompt=prompt, max_tokens=10)
```

GPT-4 accuracy: ~82%

Fine-tuned BERT: ~89%

**Why fine-tuning won:**
1. **Domain-specific**: BERT learned our internal jargon and naming conventions
2. **Consistency**: Same input always produces same output (GPT-4 can vary)
3. **Cost**: Fine-tuned BERT runs locally (free), GPT-4 costs $0.03/1k tokens
4. **Latency**: BERT inference is ~50ms, GPT-4 is ~2s

For this use case, fine-tuning was the better choice.

But if I needed *explanations* ("Why did you classify this as a bug?"), GPT-4 would be better.

## Advanced: LoRA (Low-Rank Adaptation)

Chapter 3 also introduced **LoRA** — a technique for efficient fine-tuning.

Normal fine-tuning updates all 110 million parameters in BERT. LoRA freezes the original weights and adds small "adapter" layers that you train instead.

Benefits:
- **Faster training** (fewer parameters to update)
- **Less memory** (only store adapter weights)
- **Easier to manage** (you can swap adapters for different tasks)

I re-ran my experiment with LoRA using the `peft` library:

```python
from peft import LoraConfig, get_peft_model

lora_config = LoraConfig(
    r=8,  # Rank of adapter matrices
    lora_alpha=32,
    lora_dropout=0.1,
    target_modules=['query', 'value']  # Which layers to adapt
)

model = AutoModelForSequenceClassification.from_pretrained('bert-base-uncased', num_labels=4)
model = get_peft_model(model, lora_config)

trainer = Trainer(model=model, args=training_args, train_dataset=train_data, eval_dataset=test_data)
trainer.train()
```

Results:
- **Training time**: 12 minutes (vs. 20 for full fine-tuning)
- **Accuracy**: 87% (vs. 89% for full fine-tuning)
- **Model size**: 3 MB (vs. 440 MB for full fine-tuning)

For most use cases, LoRA is the better choice. The 2% accuracy drop is worth the speed and size gains.

## Key Takeaways from Chapter 3

1. **Fine-tuning is shockingly effective** — even with just hundreds of examples
2. **Start with a pre-trained model** — don't train from scratch
3. **Use the Trainer API** — it handles all the boilerplate
4. **LoRA is great for efficiency** — especially if you're managing multiple tasks
5. **Fine-tuning beats zero-shot prompting** for domain-specific tasks
