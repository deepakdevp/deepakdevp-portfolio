# Chunking: The Most Underrated Part of RAG

I've been exploring Retrieval-Augmented Generation (RAG) for a few weeks now, and I kept hitting a frustrating problem: my retrieval results were mediocre at best.

I'd ask a question, the vector database would return "relevant" chunks, but they'd be missing context or cut off mid-sentence. The LLM would then generate answers based on incomplete information.

Then I found [Agenta.ai's guide on chunking strategies](https://www.agenta.ai/blog/rag-chunking-strategies), and everything clicked. **The problem wasn't my embeddings or my vector database — it was how I was splitting my documents.**

Chunking is the unglamorous, underappreciated foundation of every RAG system. Get it wrong, and nothing else matters.

## What is Chunking, and Why Does It Matter?

RAG systems work in three steps:
1. **Chunk** your documents into smaller pieces
2. **Embed** each chunk as a vector
3. **Retrieve** the most similar chunks when a user asks a question

Most tutorials focus on step 2 and 3 (embeddings and retrieval). Step 1 gets a throwaway line: "Just split your documents into 512-token chunks with 50-token overlap."

But that's terrible advice.

**Why chunking matters:**
- **Too large**: Chunks contain too much information, making embeddings less precise. Retrieval returns irrelevant context.
- **Too small**: Chunks lack context. The LLM gets fragments that don't make sense on their own.
- **Poor boundaries**: Splitting mid-sentence or mid-paragraph breaks semantic meaning.

The Agenta.ai article breaks down multiple chunking strategies, so I tested them on real workplace data.

## Strategy 1: Fixed-Size Chunking (The Naive Approach)

This is what most people start with:

```python
def fixed_size_chunk(text, chunk_size=512, overlap=50):
    chunks = []
    start = 0
    while start < len(text):
        end = start + chunk_size
        chunks.append(text[start:end])
        start += chunk_size - overlap
    return chunks
```

**Pros:**
- Simple to implement
- Predictable chunk sizes
- Fast

**Cons:**
- Splits anywhere, including mid-sentence
- No semantic boundaries
- Overlap is arbitrary

I tested this on our internal knowledge base (about 200 documents, ranging from API docs to troubleshooting guides). Results:

- **Precision**: 42% — retrieval often returned chunks with incomplete information
- **User satisfaction**: Low — engineers complained that answers were "technically correct but missing steps"

Example failure:
```
Query: "How do I deploy to production?"

Retrieved chunk (cut off mid-sentence):
"To deploy to production, first ensure all tests pass. Then, create a new release branch from main. Next, update the version number in package.json and commit the change. Finally, push to GitHub and"
```

The next sentence (which got cut off) explained the actual deployment command. The LLM hallucinated a deploy command instead.

## Strategy 2: Recursive Character Splitting

This improves on fixed-size by trying to split on natural boundaries (paragraphs, then sentences, then words).

```python
def recursive_split(text, chunk_size=512, separators=["\n\n", "\n", ". ", " "]):
    for sep in separators:
        if sep in text:
            parts = text.split(sep)
            chunks = []
            current = ""
            for part in parts:
                if len(current) + len(part) < chunk_size:
                    current += part + sep
                else:
                    chunks.append(current)
                    current = part + sep
            if current:
                chunks.append(current)
            return chunks
    return [text]  # Fallback to whole text
```

This is what LangChain's `RecursiveCharacterTextSplitter` does.

**Pros:**
- Respects paragraph and sentence boundaries
- More semantic coherence
- Still simple

**Cons:**
- Chunk sizes vary (some too small, some too large)
- Doesn't understand document structure (headings, lists, code blocks)

I re-ran the same test with recursive splitting:

- **Precision**: 61% — big improvement
- **User satisfaction**: Medium — answers were more complete, but still sometimes missed critical details

The deploy example now included the full paragraph, but it missed the *prerequisites* section (which was in a different chunk).

## Strategy 3: Semantic Chunking (The Smart Way)

This is where it gets interesting. Instead of splitting based on character count or delimiters, **split based on meaning**.

The idea:
1. Embed each sentence
2. Compare consecutive sentences
3. Split when similarity drops below a threshold (indicating a topic shift)

```python
from sentence_transformers import SentenceTransformer
import numpy as np

model = SentenceTransformer('all-MiniLM-L6-v2')

def semantic_chunk(text, similarity_threshold=0.5):
    sentences = text.split('. ')
    embeddings = model.encode(sentences)
    
    chunks = []
    current_chunk = [sentences[0]]
    
    for i in range(1, len(sentences)):
        similarity = np.dot(embeddings[i-1], embeddings[i])
        
        if similarity > similarity_threshold:
            current_chunk.append(sentences[i])
        else:
            chunks.append('. '.join(current_chunk))
            current_chunk = [sentences[i]]
    
    if current_chunk:
        chunks.append('. '.join(current_chunk))
    
    return chunks
```

**Pros:**
- Respects topic boundaries
- Chunks are semantically coherent
- Works well for narrative/explanatory text

**Cons:**
- Computationally expensive (need to embed every sentence)
- Chunk sizes vary widely
- Can fail on lists, code blocks, tables

Results on the knowledge base:

- **Precision**: 74%
- **User satisfaction**: High — answers felt "complete"

The deploy example now included the prerequisites AND the deployment steps, because they were semantically related.

## Strategy 4: Document Structure-Aware Chunking

This is my favorite approach from the Agenta.ai article. Instead of treating documents as flat text, **preserve their structure**.

For Markdown documents:
- Split on headings
- Keep lists together
- Preserve code blocks
- Maintain hierarchy (H1 > H2 > H3)

```python
import re

def structure_aware_chunk(markdown_text):
    chunks = []
    current_section = ""
    current_heading = ""
    
    lines = markdown_text.split('\n')
    
    for line in lines:
        # Detect headings
        if line.startswith('#'):
            if current_section:
                chunks.append({
                    'heading': current_heading,
                    'content': current_section
                })
            current_heading = line
            current_section = line + '\n'
        else:
            current_section += line + '\n'
    
    if current_section:
        chunks.append({
            'heading': current_heading,
            'content': current_section
        })
    
    return chunks
```

For our knowledge base (which is all Markdown), this worked incredibly well:

- **Precision**: 82%
- **User satisfaction**: Very high — answers were comprehensive and well-organized

The deploy example now retrieved the entire "Deployment" section, including prerequisites, steps, and troubleshooting tips.

## Strategy 5: Sliding Window with Overlap (For Context Preservation)

Sometimes you need chunks to overlap to preserve context across boundaries.

```python
def sliding_window_chunk(text, chunk_size=512, overlap=128):
    chunks = []
    start = 0
    
    while start < len(text):
        end = min(start + chunk_size, len(text))
        chunks.append(text[start:end])
        start += chunk_size - overlap
    
    return chunks
```

**When to use this:**
- Dense, interconnected text (academic papers, legal documents)
- When cross-references are common
- When you need redundancy for safety

I tested this on our API documentation (which has lots of cross-references):

- **Precision**: 78%
- **Redundancy**: High (some chunks appeared multiple times in results, which is good for context but bad for token usage)

## My Hybrid Approach for Workplace Knowledge Base

After testing all these strategies, I built a hybrid chunker:

1. **First pass**: Split by document structure (headings, sections)
2. **Second pass**: If a section is >1000 tokens, apply semantic chunking
3. **Third pass**: Add sliding window overlap (64 tokens) for long sections

```python
def hybrid_chunk(markdown_doc, max_chunk_size=1000, overlap=64):
    # Step 1: Structure-aware split
    sections = structure_aware_chunk(markdown_doc)
    
    final_chunks = []
    
    for section in sections:
        content = section['content']
        
        # Step 2: If too large, semantic split
        if len(content.split()) > max_chunk_size:
            sub_chunks = semantic_chunk(content)
            
            # Step 3: Add overlap
            for i, chunk in enumerate(sub_chunks):
                if i > 0:
                    # Prepend last N tokens from previous chunk
                    prev_tokens = sub_chunks[i-1].split()[-overlap:]
                    chunk = ' '.join(prev_tokens) + ' ' + chunk
                
                final_chunks.append({
                    'heading': section['heading'],
                    'content': chunk
                })
        else:
            final_chunks.append(section)
    
    return final_chunks
```

Results:
- **Precision**: 88%
- **User satisfaction**: Excellent
- **Token usage**: Moderate (some redundancy, but acceptable)

## Key Takeaways

1. **Chunking strategy matters more than you think** — it's not just a preprocessing step
2. **Fixed-size chunking is almost always wrong** — use semantic or structure-aware approaches
3. **Preserve document structure** when possible (headings, lists, code blocks)
4. **Test multiple strategies** on your specific data — what works for blogs won't work for API docs
5. **Hybrid approaches win** — combine structure-awareness, semantic splitting, and smart overlap
